# アーキテクチャ設計書

TechInsightのシステムアーキテクチャと設計判断を記録するドキュメントです。

---

## システム概要

TechInsightは3層構成のWebアプリケーションです。pgvectorによるベクトル類似度検索を活用し、自然言語クエリで技術記事を検索できます。

```
┌─────────────────┐     ┌─────────────────────┐     ┌──────────────────────┐
│   Next.js 14    │────▶│   FastAPI Backend    │────▶│  PostgreSQL 16       │
│   (Frontend)    │◀────│                     │◀────│  + pgvector          │
│                 │     │  ┌─────────────────┐ │     │                      │
│  App Router     │     │  │ Embedding       │ │     │  ┌──────────────┐   │
│  Tailwind CSS   │     │  │ Service         │ │     │  │ HNSW Index   │   │
│  TypeScript     │     │  │ (all-MiniLM)    │ │     │  │ (384次元)     │   │
│                 │     │  └─────────────────┘ │     │  └──────────────┘   │
└─────────────────┘     └─────────────────────┘     └──────────────────────┘
    :3000                    :8000                       :5432
```

### 検索方式

- **キーワード検索**: SQL ILIKE による部分一致検索
- **セマンティック検索**: テキストを384次元ベクトルに変換し、コサイン類似度で検索
- **ハイブリッド検索**: キーワードで候補を絞り込み、ベクトル類似度で再ランキング

## 技術スタックの選定理由

### FastAPI

| 観点 | 内容 |
|------|------|
| 選定理由 | 非同期I/O対応、自動OpenAPIドキュメント生成、Pydanticによる型安全 |
| トレードオフ | Django比でエコシステムが小さいが、本プロジェクトの規模では問題なし |

### PostgreSQL + pgvector

| 観点 | 内容 |
|------|------|
| 選定理由 | RDBとベクトル検索を単一DBで実現、運用コスト削減、SQLで統一的にクエリ可能 |
| トレードオフ | 専用ベクトルDB（Pinecone, Milvus等）と比べスケーラビリティに限界があるが、10,000件規模では十分 |

### Next.js 14（App Router）

| 観点 | 内容 |
|------|------|
| 選定理由 | Reactエコシステムの活用、App Routerによるファイルベースルーティング、TypeScriptとの親和性 |
| トレードオフ | Pages Router比で学習コストがあるが、最新のベストプラクティスに沿った設計が可能 |

### all-MiniLM-L6-v2

| 観点 | 内容 |
|------|------|
| 選定理由 | 384次元で軽量（約80MB）、CPU環境で約14ms/文の推論速度、APIキー不要 |
| トレードオフ | 大規模モデル比で精度は劣るが、技術記事検索の用途では十分な品質 |

## データフロー

### 記事登録フロー

```
ユーザー入力 (title, content, author, category)
    │
    ▼
FastAPI エンドポイント (POST /api/v1/articles)
    │
    ├──▶ Pydantic バリデーション
    │
    ├──▶ Embedding Service
    │       │
    │       └──▶ "{title} [SEP] {content}" → all-MiniLM-L6-v2 → 384次元ベクトル（L2正規化）
    │
    └──▶ PostgreSQL INSERT (記事データ + 埋め込みベクトル)
             │
             └──▶ HNSW インデックス自動更新
```

### セマンティック検索フロー

```
検索クエリ (例: "機械学習の最適化")
    │
    ▼
Next.js フロントエンド (デバウンス 300ms)
    │
    ▼
FastAPI エンドポイント (GET /api/v1/search?q=...)
    │
    ├──▶ Embedding Service
    │       │
    │       └──▶ クエリテキスト → all-MiniLM-L6-v2 → 384次元ベクトル
    │
    └──▶ pgvector コサイン類似度検索
            │
            ├──▶ HNSW インデックスで近傍探索
            ├──▶ 類似度 ≥ 0.3 のフィルタリング
            └──▶ 類似度スコア付きで結果返却
                    │
                    ▼
            フロントエンドで類似度スコア（%）を表示
```

### 各層の責務

| 層 | 責務 | 依存方向 |
|----|------|---------|
| api/v1 | HTTPリクエスト/レスポンス処理、ルーティング | → services |
| services | ビジネスロジック、ドメインルール | → models, schemas |
| models | データベーステーブル定義、ORM | なし（最下層） |
| schemas | 入出力データの型定義、バリデーション | なし |

## 設計判断の記録（ADR）

### ADR-001: ベクトルデータベースにpgvectorを採用

**ステータス**: 採用

**背景**: セマンティック検索にはベクトル類似度検索が必要。専用ベクトルDB（Pinecone, Milvus, Weaviate）とRDB拡張（pgvector）を比較検討した。

**決定**: PostgreSQL + pgvectorを採用する。

**理由**:
- RDBとベクトル検索を単一DBに統合でき、インフラ運用コストを削減
- SQLで記事データとベクトル検索を統一的にクエリ可能
- 10,000件規模では専用DBとの性能差は実用上無視できる
- PostgreSQLの信頼性とエコシステムを活用可能

**トレードオフ**: 100万件以上のスケールでは専用ベクトルDBへの移行を検討する必要がある。

---

### ADR-002: 埋め込みモデルにall-MiniLM-L6-v2を選定

**ステータス**: 採用

**背景**: テキスト埋め込み生成にはOpenAI API、Cohere API、ローカルモデル等の選択肢がある。

**決定**: sentence-transformersの`all-MiniLM-L6-v2`をローカル実行する。

**理由**:
- APIキー不要でローカル完結（外部依存ゼロ）
- 384次元で軽量（モデルサイズ約80MB）
- CPU環境でも約14ms/文の推論速度
- Hugging Face Hub から自動ダウンロード可能

**トレードオフ**: OpenAI `text-embedding-3-small` 等と比べ精度は劣るが、技術記事検索では十分な品質。

---

### ADR-003: HNSWインデックスを採用（IVFFlatではなく）

**ステータス**: 採用

**背景**: pgvectorではIVFFlatとHNSWの2種類の近似最近傍検索インデックスが利用可能。

**決定**: HNSWインデックス（m=16, ef_construction=64）を採用する。

**理由**:
- 記事の追加・更新が頻繁に発生する想定で、動的更新に対応（IVFFlatは再構築が必要）
- 10,000件規模で10ms未満の検索速度を維持
- デフォルトパラメータで精度とメモリのバランスが良好

**トレードオフ**: IVFFlat比でメモリ使用量が多く、インデックス構築が遅いが、データ規模では問題なし。

---

### ADR-004: 検索APIをGETエンドポイントとして設計

**ステータス**: 採用

**背景**: セマンティック検索APIの設計として、GET `/search?q=...` とPOST `/search` を検討した。

**決定**: GET `/api/v1/search?q=...` を採用する。

**理由**:
- RESTfulな慣例に沿った設計（検索はリソース取得=GET）
- ブラウザのURL共有・ブックマークが可能
- キャッシュ（CDN、ブラウザ）が効きやすい
- クエリパラメータでフィルタ条件を自然に表現可能

**トレードオフ**: URLの長さ制限があるが、検索クエリの長さでは問題にならない。

---

### ADR-005: 記事詳細をモーダルUIで表示

**ステータス**: 採用

**背景**: 記事一覧から詳細を表示する方式として、ページ遷移とモーダル表示を検討した。

**決定**: モーダルUIで記事詳細を表示する。

**理由**:
- 一覧画面の文脈（スクロール位置、フィルタ状態）を保持したまま詳細を確認可能
- モーダルを閉じれば即座に一覧に戻れる（ページ遷移のオーバーヘッドなし）
- ESCキー、オーバーレイクリックで閉じられるアクセシビリティ対応

**トレードオフ**: 詳細ページのURLによる直接アクセスやSEOには対応していないが、ナレッジベースの用途では一覧→詳細の往復が主要な導線。
